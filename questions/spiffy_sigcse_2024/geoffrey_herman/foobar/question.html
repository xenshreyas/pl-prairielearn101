Basic Instruction Formats ------------------------- You will need to know only these three basic instruction formats. All MIPS instructions are encoded as 32-bit pieces of data that can be parsed into smaller fields. The names of the fields and which bits are allocated to each field are shown in the figure. One important thing to notice is that the order of fields in the instruction formats do not match the order of fields in the Verilog or MIPS assembly. For example, if you had the instruction `add $5, $3, $8`, you would be assigning your data to `R[5]`. The `add` instruction's Verilog is `R[rd]=R[rs] + R[rt]`. Consequently, `$5` is `rd`, `$3` is `rs`, and `$8` is `rt`, so that the Verilog and assembly mnemonic match. Notes on Assembly Format Norms ------------------------------ * `$r **s**` is a **s** ource register exclusively, `$r **d**` is a **d** estination register exclusively, `$r **t**` **t** ransitions between being a source and a destination register * Assignment generally goes to the left for instructions that do not use the data memory (e.g., `add $rd, $rs, $rt` is assigning to `$rd`. `lui $rt, imm` is assigning to `$rt` ) * If multiple registers are used as sources, `$rs` is listed first, `$rt` is listed second (e.g., `or $rd, $rs, $rt` has two sources as does `beq $rs, $rt, imm` ) * Any instruction that reads from (e.g., `lb` or `lw` ), or writes to (e.g., `sb` or `sw` ), data memory treats `R[rs]` as a base address pointer and `imm` as an offset from that base pointer. This **base+offset** behavior is indicated by the `imm($rs)` notation, where the address of the data to be read from or written to in data memory is always `R[rs]+SignExtImm`. Consequently, all data memory instructions use the `$rt, imm($rs)` format. `$rt` transitions from being a source or a destination. Converting MIPS Assembly to Machine Code ---------------------------------------- 1. Find the MIPS assembly instruction in the Core Instruction Set table 2. Use the second-to-last column to identify the instruction's machine code format. The format will be either R, I, or J. Use the Basic Instruction Format figures to identify the fields you need for that instruction format. 3. If it's I-type or J-type format, use the last column to find the opcode (e.g., `andi` has opcode c hex and `jal` has opcode 3 hex ) and convert the hexadecimal opcode to 6-bit unsigned binary (e.g., e hex becomes 001110 and 23 hex becomes 100011).  If it's R-type format, use the last column to find the opcode (first number) and funct code (second number) (e.g., `jr` has opcode 0 and funct code 08 hex and `mfc0` has opcode 10 hex and funct code 0) and convert both to 6-bit unsigned binary. 4. If it's J-type format, take the 32-bit instruction memory address signified by the label, strip off the 4 most-significant bits (they will be added back in by `PC+4[31:28]` ) and strip off the 2 least-significant bits (they will be added back in by `2'b0` ), leaving you with the 26-bit address field for the J-type instruction. 5. If it's I-type or R-type format, use the Assembly Format column to map the fields of the assembly code to the fields of the instruction format. Convert `$rs`, `$rt`, `$rd`, and `shamt` fields into 5-bit unsigned binary (e.g., `$rs` = `$6` becomes 00110 and `shamt` = 12 becomes 01100). Convert the immediate field into 16-bit 2's complement representation (e.g., imm=24 becomes 0000 0000 0001 1000 and imm=-1 becomes 1111 1111 1111 1111). Any field that is not specified by the Assembly Format column should be all 0s (e.g., `shamt` should 00000 for `add` and `rs` should be 00000 for `lui` ). 6. Concatenate all of the fields of your instruction format together as shown in the Basic Instruction Formats diagram. Example: `or $8, $15, $20` is an R-type instruction with opcode=000000 (0 hex ), funct code=100101 (25 hex ), `$rs` = `$15` = 01111, `$rt` = `$20` = 10100, `$rd` = `$8` = 01000, `shamt` = 00000, so the machine code would be 000000 01111 10100 01000 00000 100101. #### Examples `add $5, $3, $8` maps to machine code 000000   00011    01000    00101   00000   100000 `addi $5, $3, -8` maps to machine code 001000   00011    00101    1111111111111000 `j 0x0000000c` maps to machine code 000010   00000000000000000000000011 Pseudoinstructions ------------------ Instructions that you can use when writing assembly code but are not real instructions. These instructions will be converted into real instructions by the assembler. These instructions do not have opcodes or instruction formats because they cannot be translated directly into machine code. Note: How branch pseudoinstructions get turned into real machine code can vary based on which constants or registers are used. For example, `beq $5, 4, label` would assemble to `ori $1, $0, 4       beq $1, $5, label` but `beq $5, 0xdeadbeef, label` would assemble to `lui $1, $0, 0xdead       ori $1, $1, 0xbeef       beq $1, $5, label`. Consequently, we cannot easily say how much `PC` should increment after branch pseudoinstructions. Rather than specifically indicate how much `PC` would increment, we write `PC=NextInstructionInProgram`, where `NextInstructionInProgram` is address of the instruction in your program that appears after the branch pseudoinstruction in the assembly. To uphold convention, the function that calls another function (the caller) must save the value of any caller-save register on the stack before a function call if the programmers wants to recover the value of those caller-save registers after the function call. The function that is called (the callee) is free to modify caller-save registers without breaking convention. The programmer must restore the value of caller-save registers from the stack after the function call when they wish to use those registers' value again. **Callee Save Conventions** : Registers that are saved across a function call (e.g., `$s0` and `$sp` ) by convention are considered callee-save registers. The function that is called by another function (the callee) must restore callee-save registers to their original values by the end of the function call. To uphold convention, the programmer must save any callee-save registers they plan to use onto the stack before modifying them. The programmer must restore the value of those callee-save registers from the stack before returning from the function. MIPS Style Guide MIPS Style Guidelines ===================== ### Syntax highlighting Syntax highlighting greatly enhances the readability of your code and helps catch simple mistakes like typing `$tO` vs `$t0`. ### Indentation Labels should never be indented, and instructions should always be indented one tab. You should set your tab width to 3-8 spaces and prevent your editor from expanding tabs (Google is your friend if you’re not sure how to). ### Commenting Comments are essential to understanding what your code is doing and figuring out why it might be breaking, particularly since assembly lacks such niceties as variable names, so be liberal with commenting. A helpful guideline is to make a note of which C statement (or part of a statement) each instruction corresponds to, although this isn’t always straightforward, since some statements involve a lot of intermediate steps and conditions are usually inverted. ### Instruction formatting The first operand of every instruction should be aligned; the easiest way to do this is to set your tab width to 3-8 spaces and then tab after the instruction name. Comments should also be aligned, and once again, tabs are the best way to achieve this (although you might need more than one). ### Label names Label names should be all lower case with underscores separating words. Try to make your label names meaningful but not excessively long; a good tip is to base label names on the C control structures they correspond to. Some label names are pretty generic, so to disambiguate, you can prefix them with an abbreviation of the function name. The values can be displayed in hexadecimal (Hex) or decimal (Dec). It organizes them into rows, where each row contains 4 words (each word is 4 bytes). Like the data panel, values can be shown as hexadecimal (Hex) or decimal (Dec). Values are organized in rows similar to the data panel. Unlike the data panel, the rows sit at the bottom of the panel and "grow" upwards, mimicking the behavior of a stack. ##### Output Panel This panel displays any output produced by executing the instructions. In most cases, the printing of values to output is handled by the test cases provided by the question. ##### Logs Panel This panel displays various debugger messages and information. Common things seen in this console log panel are messages about execution, reaching a breakpoint, etc. If your code contains syntax errors, those messages will show up here. * * * #### Breakpoints Breakpoints allow you to "pause" execution, letting you more easily inspect values in registers or memory in the middle of execution. Once you're done inspecting, you can "continue" execution, which will run until the next breakpoint or until the program finishes. You can add a breakpoint by clicking on a line of code in the text panel. This will pause execution at the selected instruction. A breakpoint's instruction line will be bolded so that it's distinguished from other lines. To remove the breakpoint, click on the line again. * * * #### Controls There are several controls available for controlling the execution of instructions in the text panel. ##### Scroll Checkbox By default, the text panel will automatically scroll the highlighted instruction into view during execution. If your code has bugs (e.g. an infinite loop) using max speed can heavily slow down your browser or even cause crashes, so be careful when using this speed setting. ##### Sync Code Button This button will load your code into the debugger. It will also clear all the values, remove all the breakpoints, and re-initialize the execution state so that the debugger effectively start with a clean slate. Make sure to use this button whenever you change your code. ##### Reset Button This button stops execution and re-initializes to a clean slate without removing breakpoints. This allows you to more easily "start over" without losing all your breakpoints. If you have edited your code, use the Sync Code button instead. ##### Play/Pause/Continue/Run Button This button is for running your code. Depending on the state of execution, the button will say something different. When execution hasn't started, it'll be "Play". When executing, it will say "Pause". When a breakpoint is reached, it will be "Continue". And when using max speed, it will say "Run". ##### Step Button This button lets you execute a single instruction, so you can more easily "step" through your code. This is especially useful when combined with breakpoints: set a breakpoint before some code you're unsure of, run your code up to the breakpoint, then use the step button to carefully step through the instructions that follows. * * * #### Views The debugger provides different "views" that exposes a select set of functionalities. ##### Run View This view allows you to more easily execute your code and view its output at-a-glance, by exposing a minimal set of panels and controls, and running at max speed. ##### Column View To troubleshoot your code, use the Column View to get access to the instruction text panel, setting breakpoints, and viewing register values, among other functionalities (will vary depending on the question). ##### Full View The Full View opens a fullscreen window within the page to provide a more immersive experience with the debugger. It provides almost all the panels and functionalities in the debugger. #### Expected Output Expected output for the first two test cases. You can check your code with the debugger before submitting.
